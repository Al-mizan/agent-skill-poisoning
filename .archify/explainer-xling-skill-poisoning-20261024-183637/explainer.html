Cross-Lingual Agent Skill Poisoning and Runtime Authorization

Long image

A

Answer

Cross-lingual skill poisoning bypasses static scanners in low-resource registers, but deterministic runtime policy enforcement stops execution with zero false denials.

  1. English-calibrated static scanners miss 100% of malicious prompts written in native Bangla and Banglish.1
  2. Soft prompt isolation causes severe utility collapse, reducing legitimate task completion to 76.9%.
  3. The runtime policy enforcement module intercepts proposed tool calls and eliminates policy violations in 0.038 milliseconds.2
  4. Benign tasks maintain 100% task completion rate without degrading agent capabilities.

How does the 5-stage attack lifecycle compromise agent skills?

Diagram structure
  • 1. Authoring author
  • 2. Registry publish
  • 3. Install install
  • 4. Rug-Pull rugpull
  • 5. Execution plan
  • author → publish
  • install → rugpull
  • publish → install
  • rugpull → plan · exploit
  1. Authoring ↗

    Attacker crafts a dual-intent skill using Bangla or Banglish to disguise unauthorized operations.

  2. Registry Publishing ↗

    Skill marketplace accepts the package because regex scanners only match English keywords.

  3. Installation ↗

    Agent runtime installs markdown skill into prompt context with full ambient privileges.

  4. Rug-Pull Update ↗

    Attacker mutates local skill file after install-time vetting has completed.

  5. Runtime Execution ↗

    LLM planner executes unauthorized file writes alongside benign user instructions.

How does the interactive runtime seam intercept unsafe tool calls?

Diagram structure
  • User user
  • LLM Agent agent
  • Policy Interceptor seam
  • Sandboxed Host env
  • user → agent · Run task on workspace files
  • agent → seam · Propose write_file to /tmp
  • seam → user · Prompt interactive approval dialog
  • user → seam · Deny unauthorized /tmp write
  • seam → agent · Return policy rejection error
  • agent → seam · Propose write_file to /workspace/output
  • seam → env · Dispatch authorized execution
  • env → agent · Return tool success result
  • agent → user · Return completed task answer
  1. Tool Proposal ↗

    Agent generates function call targeting out-of-scope path /tmp/canary_audit.marker.

  2. Invariant Interception ↗

    Policy interceptor catches the call before host invocation and flags path boundary violation.

  3. Interactive Gate ↗

    Human operator inspects risk metadata and chooses deterministic denial.

  4. Compliant Retry ↗

    Agent receives the rejection notice and continues execution within /workspace/output.

What architectural invariants ensure system safety?

  • Keep runtime tool authorization outside the LLM reasoning context to prevent prompt injection.
  • Validate absolute target paths against allowed workspace boundaries before calling host APIs.
  • Re-authenticate skill file hashes before dispatch to block rug-pull mutations.
  • Reject all write calls targeting sensitive system directories like /tmp, /etc, and home keys.
